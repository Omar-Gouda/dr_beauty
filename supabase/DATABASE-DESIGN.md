# Supabase database design

This is the initial schema for the current Dr. Beauty storefront. It creates tables and policies only; it contains no seed data and has not been applied or tested against Supabase.

## Tables

- `profiles` stores a small customer profile keyed to `auth.users`; an Auth trigger creates it on signup.
- `user_roles` contains explicit admin grants. Customers have no role row.
- `categories`, `brands`, `products`, `product_images`, and `product_inventory` support the catalog. Inventory is separate so anonymous catalog reads cannot reveal stock.
- `customer_addresses` stores reusable signed-in customer addresses. Orders copy the delivery details into immutable purchase-time fields, so later address edits do not alter order history.
- `orders` and `order_items` support authenticated customer COD checkout. The order number is generated by PostgreSQL. Item totals and order totals are generated/checked by the database; purchase snapshots cannot be changed after insertion.
- `product_reviews` supports moderation and permits submissions only from a signed-in customer with a qualifying order. Only approved reviews are public.
- `wishlist_items` is private to its customer.
- `newsletter_subscribers` stores normalized email, consent, confirmation state, and hashes of unsubscribe/confirmation tokens. It has no public read or write policy.
- `promotions` stores percentage or fixed EGP discounts, validity, minimum subtotal, and an optional redemption cap.
- `email_campaigns` and `email_deliveries` store email and WhatsApp delivery state. Channel-aware idempotency and order/campaign recipient constraints prevent duplicate queue rows; attempt and lease fields support retries.

Prices use exact `numeric` values in EGP. Foreign keys, status checks, timestamps, indexes, and RLS are included. Tables exposed in `public` have RLS enabled. The `private` helper schema is not exposed through the Data API by the SQL migrations: schema exposure is a separate Supabase API setting, not controlled by SQL grants. In the Supabase Dashboard, open **Project Settings > API > Exposed schemas** and ensure `private` is absent. Keep it absent; the authenticated schema usage grant is needed for RLS policies to call helper functions, and does not itself expose the schema through the Data API. This repository has a `supabase/config.toml` for local Auth templates and the notification Edge Function; it does not modify a hosted project's dashboard settings.

## Security model

RLS uses `auth.uid()` for customer-owned rows. Customers can access only their own profiles, addresses, orders, order items, pending reviews, and wishlists. Profile column grants omit role fields; the role table has RLS enabled and no API grants or customer policies. Admin policies call `private.is_admin()`, a fixed-search-path security-definer helper that checks the protected role table without querying it recursively through RLS.

Product, category, brand, image, current promotion, and approved-review reads are public. Inventory, customer addresses, newsletter subscribers, campaign deliveries, and unapproved reviews are not public. Newsletter and email-delivery writes are reserved for trusted server processing.

The migration grants database admin policies only to authenticated users with an admin row. Application pages and every server action/route must still verify authorization server-side. Never trust a client-supplied price, stock value, role, order status, or total. There is no customer/anonymous insert policy for orders. Checkout must run through a trusted server-side transactional operation: validate the session when present, reload current prices and stock, calculate shipping and discounts, and enforce promotion eligibility and redemption limits under concurrency. Order creation and stock reservation/decrement must commit atomically, so neither can succeed without the other. Use row locks or conditional inventory updates and roll back the transaction if any item is unavailable or any check fails. The service-role key bypasses RLS; if used by that server, it must remain server-only and the server must perform these checks itself.

The additive `20261022000000_admin_authorization_rpc.sql` migration exposes only `public.is_current_user_admin()`, a boolean check for the caller's own session. Execution is granted to authenticated users only; it accepts no user ID and does not expose `user_roles`. Apply this migration after the initial schema before using the application admin routes. The UI and server actions fail closed if the RPC is missing or errors, and data mutations still run under the user's session so table RLS policies remain in force.

### Authenticated COD order RPC

The additive `20261023000000_cod_order_creation.sql` migration adds nullable `orders.idempotency_key` for compatibility with any existing order rows and a unique constraint on `(user_id, idempotency_key)`. New orders created by the RPC always include a key, and the check constraint prevents a keyed guest order. Apply this migration after the initial schema and admin RPC migration.

`public.create_cod_order(...)` accepts a product/quantity JSON array, a client-generated UUID idempotency key, and customer delivery/contact fields. It accepts no user ID, price, stock, shipping, discount, status, or total. The function requires `auth.uid()`, reads the customer email from `auth.users`, and is executable only by `authenticated`. Its `SECURITY DEFINER` body pins an empty `search_path`, qualifies referenced objects, and validates all inputs because it runs with elevated table privileges. Existing table grants and RLS policies are unchanged.

Retries using the same customer/key are serialized with a transaction advisory lock and return the existing safe order number, status, total, and currency only when the normalized request matches. Apply `20261024000000_cod_order_idempotency_payload.sql` after the initial schema, admin RPC, and COD order RPC migrations. It adds a RLS-enabled, non-Data-API `private.cod_order_idempotency` table and binds each `(user_id, idempotency_key)` to a canonical JSONB request payload. The payload is computed inside PostgreSQL; it includes sorted product UUID/quantity pairs, trimmed customer and delivery fields, and a trimmed, case-folded promotion code. The browser cannot supply the binding. A retry with a different normalized payload receives an explicit safe error and does not reuse the order; the original order and inventory remain unchanged. Existing keyed orders are backfilled from their immutable order and item snapshots.

The RPC still requires `auth.uid()` and retains its authenticated-only execution grant. The advisory transaction lock serializes same-key requests, while the private table primary key and the existing unique `(user_id, idempotency_key)` order constraint provide uniqueness backstops. For a new request, order creation, item snapshots, inventory decrement, and idempotency binding share one transaction; any error rolls all of them back. Product and inventory rows are locked in ascending product UUID order before price/stock checks. The function rejects missing/inactive products, duplicate IDs, invalid quantities, or insufficient stock, then writes server-priced order snapshots and decrements inventory. Existing deferred order-total triggers verify the item subtotal before commit. Stock is decremented when the pending COD order is created. The additive lifecycle migration below supplies an authenticated admin transition RPC and transactional cancellation/restock operation; until it is applied, the application must not expose order-status mutations.

### COD order confirmation email queue

Apply `20261025000000_cod_order_confirmation_enqueue.sql` after the initial schema and the admin, COD order, and payload-idempotency migrations. It adds an `AFTER INSERT` trigger on `public.orders`; in the same transaction, the trigger inserts one `queued` row into `public.email_deliveries` with the internal `orders.id`, the order's `customer_email`, and a deterministic `order-confirmation:<order UUID>` idempotency key. At this stage the partial unique index on `(order_id, delivery_type)` prevents duplicate confirmation rows; the WhatsApp migration later extends it to include channel. The trigger uses a fixed-search-path `SECURITY DEFINER` function because the authenticated order RPC has no direct insert grant for email deliveries. No client-facing policy or grant is added, and the existing admin-only read policy remains in force. The queue contains no message body or copied address/order details. Orders without a valid recipient email fail atomically rather than being created without a confirmation queue record. Existing historical orders are not backfilled or emailed by this migration.

Enqueueing does not send mail and does not set `sent`. The database claim, completion, and failure contract is defined in `20261028000000_notification_worker_claims.sql`; a trusted worker must claim a short batch, commit before contacting the provider, and load message details from the referenced persisted order and item snapshots. It records `sent` only after provider confirmation. Transient failures use bounded backoff; exhausted and permanent failures use `terminal_failed` for operator review. Use the delivery idempotency key with a provider that supports idempotent sends; without provider support, a worker crash after provider acceptance but before recording `sent` can still cause a duplicate external email. No worker or provider is implemented here.

### Notification worker database contract

Apply `20261028000000_notification_worker_claims.sql` after migrations `20261021000000` through `20261027000000`. It adds `email_deliveries.claim_token`, the `terminal_failed` status, a partial index for eligible transactional rows, and a partial index for expired processing leases. Existing queue rows and their statuses remain intact; existing `failed` rows remain retryable subject to their existing `next_attempt_at` and attempt count. Newsletter campaign rows remain in the queue but are deliberately excluded from worker claims.

The migration exposes three `SECURITY DEFINER` functions with an empty fixed `search_path`: `public.claim_order_notifications(p_batch_size integer default 10, p_lease_seconds integer default 120)`, `public.complete_order_notification(p_delivery_id uuid, p_claim_token uuid, p_provider_message_id text default null)`, and `public.fail_order_notification(p_delivery_id uuid, p_claim_token uuid, p_error_code text)`. Execution is revoked from `PUBLIC`, `anon`, and `authenticated`, and granted only to the already-used Supabase `service_role`. This role is the repository's existing trusted server boundary: earlier migrations grant it table privileges, while customer APIs use the authenticated session. Keep its credential only in a separately secured worker runtime; never use it in browser code or the customer's cookie client. These functions do not expose a table policy or queue read grant to customers.

Claims are atomic: eligible rows are locked with `FOR UPDATE SKIP LOCKED`, moved to `processing`, assigned a fresh UUID fence, leased using database time, and have `attempt_count` incremented in the same statement. Batch size is limited to 1 to 25 and lease duration to 30 to 900 seconds. An expired or missing legacy lease is reclaimable with a new token. Completion and failure require the row still to be `processing`, the exact current token, and a lease that has not expired; a stale or expired claim is rejected. Successful completion stores the provider reference (optional, trimmed, maximum 500 characters), `sent_at`, and `sent` only after the worker receives provider confirmation.

The database retry policy is five total claims per delivery. `fail_order_notification` accepts only an enumerated error code, never raw provider error text. `provider_timeout`, `provider_unavailable`, `rate_limited`, and `unknown_failure` are retryable with 30, 60, 120, then 240 seconds of delay; all other accepted codes are terminal. The fifth failed attempt becomes `terminal_failed`. A claim pass also closes exhausted queued/failed rows and expired final attempts. Invalid WhatsApp consent evidence is terminally suppressed before claim. Worker code must classify errors using these exact codes and must not log provider responses or personal data.

Only `email` or `whatsapp` rows for order-linked `order_confirmation` or `order_update` messages can be claimed; newsletter campaigns are excluded. Email delivery uses the stored `recipient_email` snapshot and order/item data loaded from the referenced persisted order. At claim time, WhatsApp requires `private.cod_order_idempotency.whatsapp_consent = true` and the matching order-specific WhatsApp confirmation evidence with the same phone, consent timestamp, source `checkout`, and version `cod-order-whatsapp-v1`. Missing or mismatched evidence is terminally suppressed. This is transactional order messaging only; the claim functions have no marketing eligibility.

The isolated Node entry point is `scripts/notification-worker.mjs`. Run `node scripts/notification-worker.mjs` (or `node scripts/notification-worker.mjs --dry-run`) for the default dry run. It checks only whether the required Supabase URL and secret-key configuration is present and well-formed; it does not create a client, contact Supabase, claim jobs, update rows, or call providers. It reports missing/invalid variable names and safe booleans only. Node does not load `.env.local` automatically; inject environment variables through a trusted local shell or worker secret store. No package script, schedule, HTTP endpoint, provider adapter, or deployment platform is configured.

The normal Next.js cookie helper uses the publishable key and cannot execute these RPCs. The worker's privileged Supabase client uses the existing `@supabase/supabase-js` dependency with `NEXT_PUBLIC_SUPABASE_URL` and a server-only `SUPABASE_SECRET_KEY`. The current Supabase secret API key authenticates as the database's `service_role`; that role is explicitly granted these three RPCs in the migration. The secret key bypasses RLS and must exist only in the isolated server process's secret store, never in client code or environment files committed to the repository. Configure the key in the Supabase dashboard and worker host before any live processing.

There is no provider implementation. CLI `--live` therefore fails closed before client creation or claim. The exported `runNotificationBatch` hook can process at most one batch (default 10, maximum 25; lease 30 to 900 seconds) only when trusted server code supplies both email and WhatsApp adapters. It calls only the three RPCs above, passes the exact current claim token on completion/failure, and stops between messages when its shutdown signal is aborted; unprocessed claims are left for lease recovery. Adapters receive the queue snapshot and idempotency key, must load/verify persisted order and item snapshots for email content, must use only transactional message types, and may report a retryable/permanent failure only when the provider confirms the message was not accepted. An ambiguous delivery or completion result is left leased for recovery rather than immediately failed, because retrying may duplicate a provider-accepted message. The hook is not invoked by the CLI and no messages were sent.

Before production, implement and configure provider adapters, a trusted worker host/scheduler, international WhatsApp phone validation with country context, and provider-approved transactional templates. WhatsApp eligibility is checked by the claim RPC against the order-specific consent binding and confirmation evidence; the adapter must never send marketing. Provider idempotency may reduce duplicates, but a provider can accept a send while the worker loses the response, so exactly-once delivery is not guaranteed. No Supabase connection or provider delivery was performed.

### Trusted email order snapshot resolver

Apply `20261030000000_email_order_snapshot_resolver.sql` after `20261029000000_order_notification_event_links.sql`. It adds `public.resolve_order_email_snapshot(p_delivery_id uuid, p_claim_token uuid)`, a `SECURITY DEFINER` table-returning RPC with `set search_path = ''`. Execution is revoked from `PUBLIC`, `anon`, `authenticated`, and initially from `service_role`, then granted only to `service_role`. It does not change claim, completion, or failure RPC signatures or grants. The function accepts no user ID or browser session and exposes no public order lookup.

The resolver requires the delivery row to remain `processing`, the exact current `claim_token`, and an unexpired `locked_until`; it locks the delivery while validating. It accepts only `channel = 'email'`, `delivery_type in ('order_confirmation', 'order_update')`, an order-linked row, and null campaign/subscriber references. Stale claims, expired leases, unsupported types/channels, and inconsistent relationships raise the generic `P0001` error `The email notification snapshot is unavailable.`

The typed result is one row per persisted item, ordered by item creation time and ID, with order-level fields repeated:

- Delivery context: `delivery_id uuid`, `channel text`, `delivery_type text`, `recipient_email text`, `idempotency_key text`, `notification_status text`, `notification_event_at timestamptz`, and `event_from_status text`.
- Order snapshot/current state: `order_number bigint`, `customer_name text`, `order_created_at timestamptz`, `current_order_status text`, `currency text`, `subtotal numeric(14,2)`, `shipping_amount numeric(12,2)`, `discount_amount numeric(14,2)`, and `total_amount numeric(14,2)`.
- Item snapshot: `item_id uuid`, `product_name_snapshot text`, `product_slug_snapshot text`, `quantity integer`, `unit_price numeric(12,2)`, and `line_total numeric(14,2)`.
- Shipment data: `shipping_carrier text`, `tracking_number text`, and `tracking_url text`; populated only when the linked event has `to_status = 'shipped'`, and null for confirmations and other updates.

The delivery's `order_id` joins to `orders.id`; item rows are selected only for that order. The returned recipient must exactly equal the immutable `orders.customer_email` snapshot. Order number, customer name, creation time, current state, currency, and monetary values come from `public.orders`. Item name, slug, quantity, unit price, and generated line total come only from immutable `public.order_items` snapshots; current catalog data is never used. The function verifies at least one item and checks item totals against the stored subtotal and order arithmetic.

For `order_confirmation`, `status_event_id` and queued `order_status` must be null and `status_payload` must be `{}`; `notification_event_at` is `orders.created_at`. Current order status is returned separately and is not represented as the original confirmation state. For `order_update`, the function resolves only `email_deliveries.status_event_id` and requires the event's order and `to_status` to match the delivery. It returns `event_from_status` and the event's `changed_at`; it does not infer an event from current state or timestamps. Shipment fields come only from that linked event and must match `status_payload` and the HTTPS URL constraint. Other update payloads must be empty.

Missing order/item/event data, an empty item set, recipient mismatch, invalid snapshots, inconsistent totals, stale/expired claims, or event/payload disagreement fail closed with the same generic error and no partial rows. The function does not return phone, address, promotion internals, user ID, consent evidence, or queue error details. It does not send or mark messages sent; provider delivery remains unimplemented.

**Status-event association migration:** `20261029000000_order_notification_event_links.sql` adds nullable `email_deliveries.status_event_id uuid`, a foreign key to `private.order_status_events(id)`, and a partial index. It adds a unique index on `(order_id, to_status)` so the lifecycle relationship is database-enforced. A fixed-search-path private trigger associates each new order update with the already-inserted event in the same transaction, validates that `order_status` matches `to_status`, and checks shipment payload fields against that event. Confirmation and newsletter rows must keep `status_event_id` null. The migration does not alter the claim/complete/fail RPC signatures or their grants; the existing email-delivery RLS policies and table grants remain in force.

Historical order updates are backfilled only by exact `(order_id, order_status = to_status)` matches. Before the backfill, the migration checks for duplicate status events, missing or non-unique matches, and payload disagreement (including exact shipment carrier/tracking values and empty payloads for non-shipped updates). It raises an exception and rolls back the entire migration if any such ambiguity or inconsistency exists; it does not infer links from current order status or timestamps. If that preflight fails in a deployed database, investigate and reconcile the records explicitly before retrying. This migration is additive and has not been applied or tested against a database in this phase.

After applying the event-association and resolver migrations, the resolver uses `status_event_id` to load the exact originating event instead of relying on a status-name or timestamp join. Confirmation notices continue to use the immutable order creation snapshot and are not linked to lifecycle events.

The resolver provides a least-privilege worker read path instead of direct reads under the broad `service_role` table grants. The existing Node worker has not been changed to call the resolver. The local Edge Function scaffold below does call it after an email-only claim; it has not been deployed or run.

Minimum tests before deployment: verify result field names/types against schema; allow `service_role` and deny `anon`/`authenticated`; reject stale/expired claim tokens; resolve confirmation and recipient equality; resolve each lifecycle status to exactly its linked event; validate shipped event/payload/HTTPS consistency; fail closed for missing order/items/event, empty items, recipient mismatch, or inconsistent totals; verify catalog edits cannot affect historical item snapshots; verify concurrent claims cannot resolve another worker's claim; and verify the worker suppresses sending when resolution fails. Run these against an isolated PostgreSQL database after applying the migrations; none were run in this phase.

### Supabase Edge Function + Resend email worker

**Existing database behavior:** the original `public.claim_order_notifications(p_batch_size integer default 10, p_lease_seconds integer default 120)` claims both email and WhatsApp. Its return fields are `delivery_id uuid`, `channel text`, `delivery_type text`, `order_id uuid`, `recipient_email text`, `recipient_phone text`, `idempotency_key text`, `order_status text`, `status_payload jsonb`, `attempt_count integer`, `claim_token uuid`, and `lease_expires_at timestamptz`. It must not be used by an email-only consumer because that would lease WhatsApp work.

**New local migration, not applied:** `20261031000000_email_only_notification_claims.sql` adds `public.claim_order_email_notifications(p_batch_size integer default 1, p_lease_seconds integer default 120)`. It returns the same columns and types as the shared claim RPC. Its supported bounds remain batch size 1–25 and lease 30–900 seconds. It selects only order-linked `channel = 'email'` rows of type `order_confirmation` or `order_update`; it excludes campaign/subscriber rows. Expired email leases are reclaimable with a new UUID claim token and incremented attempt count. It marks exhausted eligible email work `terminal_failed` using the existing five-attempt rule. `FOR UPDATE SKIP LOCKED` and the atomic update retain concurrency safety. Unlike the shared claim operation, this RPC performs no WhatsApp consent suppression and does not read or mutate WhatsApp rows at all, including exhausted or expired rows. It reuses the current worker due/lease indexes. Execution is revoked from `PUBLIC`, `anon`, `authenticated`, and `service_role`, then granted only to `service_role`; the function has `SECURITY DEFINER` and an empty fixed `search_path`. This additive migration is unparsed/unapplied and needs isolated PostgreSQL validation.

The local JavaScript Edge Function is `supabase/functions/notification-email-worker/index.js`, with `templates.js` and the isolated Resend adapter in `resend.js`. `supabase/config.toml` sets its JavaScript entry point and keeps `verify_jwt = true`. The handler requires a gateway-verified JWT whose role claim is `service_role`, plus an `x-notification-scheduler-token` matching the high-entropy `NOTIFICATION_SCHEDULER_TOKEN` secret (configure at least 32 random characters). It accepts only POST, ignores request bodies, takes no delivery IDs from callers, and claims at most one job with `p_batch_size = 1` and `p_lease_seconds = 120`. The handler uses the runtime-injected `SUPABASE_URL` and server-only `SUPABASE_SERVICE_ROLE_KEY` for PostgREST RPC calls; it never returns or logs either credential. This scaffold currently relies on the legacy injected service-role JWT being available both to the runtime and scheduler; confirm that remains enabled for the target project before deployment. The Supabase key bypasses RLS, and the RPC grants remain the database authorization boundary. The normal application never imports this function.

The exact resolver call is `public.resolve_order_email_snapshot(p_delivery_id uuid, p_claim_token uuid)`. The exact existing completion and failure calls are `public.complete_order_notification(p_delivery_id uuid, p_claim_token uuid, p_provider_message_id text default null) returns void` and `public.fail_order_notification(p_delivery_id uuid, p_claim_token uuid, p_error_code text) returns text`. The Edge handler carries the claim token through resolution and completion/failure; stale/expired tokens remain rejected by those SQL RPCs. A resolver transport/error result is deferred to lease recovery. A valid RPC response with malformed or unsupported snapshot data is terminally failed with the existing `invalid_message` code. No direct queue table reads or writes were added.

Templates use only resolver output: recipient email, customer name, order number, persisted item names/quantities/line totals, stored order total/currency, the exact notification status/event, and shipment carrier/tracking number/HTTPS URL on the shipped event. Confirmation, confirmed, processing, shipped, delivered, and cancelled messages are rendered from fixed copy; update copy uses the originating `notification_status`, never the potentially newer `current_order_status`. Dynamic names and item text are HTML escaped. No storefront origin, product links, address, phone, payment, or promotion data is used. `RESEND_FROM_EMAIL` must be a verified sender address; no base site URL is needed. The resolver does not provide delivery address, customer phone, payment method/status, or promotion details; templates requiring them need a separately reviewed resolver change. There is no template-version column, so preserve deterministic template output for queued retries and assess pending messages before changing template content.

The Resend adapter reads `RESEND_API_KEY` from Edge Function secrets and `RESEND_FROM_EMAIL` as a server-side sender setting; that address must belong to a verified Resend domain. It uses the fixed `https://api.resend.com/emails` endpoint and the database `idempotency_key` as the provider `Idempotency-Key`. A 2xx response must contain a bounded provider message ID before the worker calls completion. Explicit 429 responses call failure with `rate_limited`; explicit 401/403 responses use the existing retryable `unknown_failure` code; other explicit 4xx rejection responses use `provider_rejected` and become terminal under the current SQL policy. Network errors/timeouts, HTTP 408/409/5xx, redirects, malformed success responses, and ambiguous database completion results are deferred without immediate failure. Lease recovery retries the same delivery with the same idempotency key. This remains at-least-once behavior: Resend documents that idempotency keys are retained for 24 hours, so later retries can duplicate a send; exactly-once delivery is not guaranteed. No recipient, message body, provider response, or token is logged. The local adapter code was not invoked and no email was sent.

**Production scheduling is not configured.** Supabase Cron requires `pg_cron` and `pg_net` enabled plus a recurring schedule that POSTs to the deployed function. Use Vault for the project URL, publishable `apikey`, service-role JWT in the `Authorization: Bearer` header, and `NOTIFICATION_SCHEDULER_TOKEN` in `x-notification-scheduler-token`. The Edge runtime also needs its injected `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY`, plus the `RESEND_API_KEY` secret and verified `RESEND_FROM_EMAIL` setting. Keep gateway JWT verification enabled, and have the handler continue checking both the service-role claim and the scheduler token. Monitor Cron runs and Edge Function outcomes. Supabase documents Cron + `pg_net` invocation and Vault-held credentials in its [scheduling guide](https://supabase.com/docs/guides/functions/schedule-functions); the function JWT default/headers and JavaScript entrypoint are documented in [function configuration](https://supabase.com/docs/guides/functions/function-configuration) and [authorization headers](https://supabase.com/docs/guides/functions/auth-headers). Resend's [idempotency contract](https://resend.com/changelog/idempotency-keys) documents its 24-hour retention. No schedule, Vault entry, remote secret, function deployment, or external call was created in this phase.

Overlapping authenticated invocations are safe at the queue level: the email claim uses row locks with `SKIP LOCKED`, so they cannot own the same eligible row simultaneously. There is no lease-renewal RPC. The scaffold claims one message per invocation, uses a 120-second lease and bounded database/provider requests, and leaves uncertain provider or completion outcomes leased for recovery. Do not increase batch size or shorten the schedule without isolated tests that prove the full processing path fits the lease. Before replacing the Node worker, validate migration syntax, grants and isolation, concurrent claims, lease recovery/fencing, retry exhaustion, scheduler authentication, template escaping, provider status classification, idempotency behavior, and redacted logs in an isolated Supabase project with a Resend test configuration. Keep `scripts/notification-worker.mjs` available until the Edge replacement has passed independent review/testing and is explicitly approved.

### COD WhatsApp confirmation foundation

Apply `20261026000000_whatsapp_cod_notifications.sql` after the initial schema and migrations `20261022000000_admin_authorization_rpc.sql` through `20261025000000_cod_order_confirmation_enqueue.sql`. The order snapshot stores the checkout phone in `orders.customer_phone`. The base `create_cod_order(...)` RPC remains email-only. The checkout Server Action uses `create_cod_order_with_whatsapp_consent(...)` with the customer's persisted explicit choice; false delegates to the same email-only order flow, while true additionally enqueues WhatsApp.

The new migration extends `email_deliveries` with a channel, a channel-specific recipient, and consent evidence. It replaces the order/type unique index with a per-order/type/channel unique index while preserving all existing email rows as `channel = 'email'`. WhatsApp delivery rows require a phone, a database timestamp, the checkout source, and the consent-copy version `cod-order-whatsapp-v1`. The current optional checkbox copy for that version is: “I agree to receive optional transactional WhatsApp messages about this order, including confirmation and delivery updates. This consent does not cover marketing messages.” The checkout submits the explicit boolean to the wrapper; a false choice delegates to the email-only flow. Order creation, stock changes, email enqueue, consent binding, and WhatsApp enqueue share the same database transaction. A consent choice is bound to the customer/idempotency key on first wrapper use; retrying with a different choice is rejected. Repeated same-choice retries cannot create another channel row. The RPC records the caller's explicit consent assertion; it cannot prove that the user saw the checkbox. Declining consent still allows COD ordering.

The stored phone is the customer's original checkout value, not a validated international destination. A trusted WhatsApp adapter must normalize it with a maintained phone-number library and an explicit country context, validate E.164 formatting, and suppress delivery if it is invalid; do not infer international format from the phone alone or rewrite the immutable order snapshot. The adapter must use a configured provider and an approved WhatsApp template for the account/recipient, with template variables built from server-side order data. Keep provider credentials server-only. Queue claiming, retries, and terminal failure handling are defined in `20261028000000_notification_worker_claims.sql`; never mark a row sent at enqueue time. Phone normalization, providers, and message delivery remain unimplemented.

Shipping follows the existing storefront rule: EGP 60 for a positive subtotal up to EGP 1,000, free above EGP 1,000. A supplied promotion is reloaded by case-insensitive code, locked for the transaction, and checked for active dates, minimum subtotal, and redemption capacity. Redemption capacity counts non-cancelled orders; locking the promotion serializes new redemptions of that code. Percentage/fixed discounts and any maximum discount are calculated from exact `numeric` values. The confirmation queue trigger creates a pending delivery record only; it does not send or claim notification success. The checkout calls the authenticated consent-aware wrapper and retains the same idempotency key and consent choice for retries of one submission.

### Order lifecycle, shipment tracking, and cancellation

Apply `20261027000000_order_lifecycle.sql` after migrations `20261021000000` through `20261026000000`. It adds `orders.shipping_carrier`, `tracking_number`, `tracking_url`, `shipped_at`, `cancelled_at`, `status_changed_at`, and `inventory_restored_at`; it does not alter purchase snapshots. Carrier and tracking strings are trimmed and length-limited. A tracking URL must match the migration's HTTPS-only URL validation, which rejects alternate schemes and whitespace. A tracking number is required before shipment. Tracking data is preserved through later transitions unless explicitly supplied during an authorized transition. No carrier integration or automatic tracking is provided.

`public.transition_cod_order_status(p_order_id, p_new_status, p_shipping_carrier, p_tracking_number, p_tracking_url)` derives the caller from `auth.uid()`, checks `private.is_admin()`, and is executable only by `authenticated`. It locks the order before evaluating and recording a transition. Allowed transitions are:

| Current status | Allowed next status |
| --- | --- |
| `pending_confirmation` | `confirmed`, `cancelled` |
| `confirmed` | `processing`, `cancelled` |
| `processing` | `shipped`, `cancelled` |
| `shipped` | `delivered` |
| `delivered` | none |
| `cancelled` | none |

Repeating the current status is an idempotent no-op only when no tracking change is requested. Every actual transition writes a private status event and updates `status_changed_at`. Cancellation is accepted only for `pending` or `failed` payment states. It locks each inventory row in ascending product UUID order, restores quantities from immutable `order_items`, records each `(order_id, product_id)` once in the private restoration ledger, and sets `inventory_restored_at` in the same transaction as the cancelled state. Missing items/inventory, a prior restoration marker/ledger row, or integer overflow aborts the whole transaction. The order row lock serializes concurrent attempts for the same order; the terminal cancelled state makes later repeats no-ops. Historical orders already cancelled before this migration are not automatically restocked or backfilled and require manual reconciliation.

The migration revokes authenticated direct updates to `orders.order_status`; status changes must use the RPC. It adds private status-event and inventory-restoration tables with RLS enabled and no API-role grants. Each real transition enqueues an `order_update` row in `email_deliveries` in the same transaction. Shipment notices carry carrier, tracking number, and tracking URL in `status_payload`, and are queued only on the actual transition to `shipped`. A partial unique index permits only one row per order, status, and channel, so repeated transitions cannot duplicate notices. WhatsApp rows are enqueued only when the private checkout binding records consent and the matching consent-bound WhatsApp confirmation evidence is present; missing evidence suppresses WhatsApp. Queuing does not send or mark a message sent. The worker migration adds the explicit `terminal_failed` state and the restricted claim, completion, and failure contract described above. A worker runtime must still be deployed separately.

Customers must retrieve tracking through an authenticated order view scoped to their own `orders.user_id = auth.uid()` (with the existing own-order RLS policy also enforced). Tracking details are protected order columns, never lookup credentials. Do not provide public order-number or tracking-number lookup endpoints. The current customer receipt route is a placeholder and there is no customer order-detail page; the minimal application follow-up is an authenticated server-rendered order detail/receipt route that queries only the current user's row and displays status, shipped time, carrier, tracking number, and the validated HTTPS URL. The admin order list is read-only; an admin action may call the transition RPC after this migration is applied.

### Admin bootstrap

1. Create and verify the intended administrator account through Supabase Auth.
2. As the project owner, obtain that account's Auth user UUID and run the following in the Supabase SQL Editor, replacing the UUID placeholders there (do not put credentials in this SQL file):
   ```sql
   insert into public.user_roles (user_id, role, granted_by)
   values ('<ADMIN_AUTH_USER_UUID>'::uuid, 'admin', '<GRANTING_OWNER_AUTH_USER_UUID>'::uuid)
   on conflict (user_id) do update
   set role = excluded.role, granted_by = excluded.granted_by, granted_at = now();
   ```
3. Revoke admin access by deleting that user's `user_roles` row. Only project owners/migration administrators should perform these operations; do not expose role-table writes through the app.

### Persistent admin notifications

The local, additive migration `20261102000000_admin_notifications.sql` introduces `public.admin_notifications`. It is required because the existing schema has no durable admin inbox or read/unread state; customer-facing `email_deliveries` are outbound email/WhatsApp work and are not an admin notification store. It has not been applied or validated against PostgreSQL in this workspace.

The table stores only the recipient Auth user UUID, event type, order UUID, optional originating private status-event UUID, creation time, and nullable `read_at`. Unique partial indexes prevent duplicate order-created entries per administrator/order and duplicate cancellation entries per administrator/status event. Recent and unread access paths are indexed. No historical notifications are backfilled.

Two fixed-search-path `SECURITY DEFINER` triggers create rows transactionally: after a persisted order insert (`order_created`) and after an inserted `private.order_status_events` row whose `to_status` is `cancelled` (`order_cancelled`). The order lifecycle RPC records status events inside the same transaction as the status and stock changes, so a notification insert failure rolls that transition back. Only users already present in `public.user_roles` with `role = 'admin'` at event time receive an entry. Migration `20261103000000_customer_service_requests.sql` adds notifications for persisted Beauty Tips and support requests and non-cancellation order-status events; those changes are additive and remain local until reviewed and applied.

RLS permits authenticated admins to read/update only their own inbox rows while `private.is_admin()` is true. Authenticated table grants are limited to `SELECT` and `UPDATE(read_at)`; inserts and other mutations are trigger-only. Admin Server Actions independently re-check the session and admin RPC, and constrain updates to the current recipient. The Admin Header displays the latest 20 notifications and unread count; order and customer-request links lead to their admin review pages. The existing role and order policies remain unchanged.

The current project does not configure a Realtime publication for this table. The center refreshes its server data when opened and offers an explicit refresh control; it does not promise push delivery while an admin is idle on a page. Notifications remain in PostgreSQL so they are still available after offline periods and later visits.

### Administrator new-order email outbox — local implementation

`20261105000000_admin_order_email_outbox.sql` adds a private outbox separate from customer `email_deliveries`. An `AFTER INSERT` trigger on `public.admin_notifications` handles only `order_created` events, verifies the corresponding `user_roles` row, and snapshots that administrator's `auth.users.email`. It creates one uniquely keyed row per `(order_id, recipient_user_id)`. Invalid or unavailable Auth email is retained as a terminal `invalid_recipient` record rather than being silently treated as delivered. No recipient is accepted from the browser.

The outbox is inaccessible to API roles directly. Its fixed-search-path `SECURITY DEFINER` claim, completion, and failure RPCs are executable only by `service_role`. Claims use `FOR UPDATE SKIP LOCKED`, a per-claim UUID fencing token, expiring leases, a five-attempt ceiling, and bounded 30/60/120/240-second retry delays. The Edge email worker claims at most one customer email and one administrator email in each invocation; it validates the separate `admin_order_created` result and sends each administrator individually with the existing Resend adapter and the row's deterministic idempotency key. The admin template uses only the persisted order number, creation time, customer name, total, and currency; it does not disclose other recipients or include customer contact details. Provider acceptance is required before the worker calls completion. Ambiguous provider outcomes defer to lease recovery, so delivery is at least once and not guaranteed exactly once.

The asynchronous provider send happens after order commit, so provider rejection, timeout, or outage does not roll back a successfully created order. Outbox insertion itself is in the order transaction through the existing admin inbox trigger; a database failure while persisting that outbox row can still fail the order transaction. The migration and worker changes are local and unvalidated against PostgreSQL or a deployed Edge Function. The worker reuses `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `NOTIFICATION_SCHEDULER_TOKEN`, `RESEND_API_KEY`, and `RESEND_FROM_EMAIL`; this repository cannot establish whether hosted secrets or a schedule are configured. WhatsApp remains separate and is not required for checkout or administrator email.

### Customer consultation and support requests — local implementation

The additive migration `20261103000000_customer_service_requests.sql` creates `public.customer_service_requests` for authenticated Beauty Tips and customer-support requests. It stores the Auth user reference, request category and text, optional product or owned-order reference, selected contact method and contact value, and status/timestamps. Internal notes live in the separate admin-only `public.customer_service_request_notes` table, so a customer's own-request read cannot expose staff notes. Authenticated customers can read only their own request rows; admins can read the request queue and notes and change status/notes only through a privileged RPC. Direct table inserts or updates are not granted. `public.submit_customer_service_request` is a fixed-search-path `SECURITY DEFINER` RPC executable only by `authenticated`; it derives `customer_id` from `auth.uid()`, derives email replies from `auth.users`, validates the allowed category/type pairing, requires owned order references for order-specific support categories, and verifies an optional product is active. A trigger creates a deduplicated admin inbox notification in the same transaction. If no administrator receives the notification, submission rolls back rather than returning a false success. `public.update_customer_service_request` independently requires the protected admin helper and changes request status and admin-only notes transactionally.

## Decisions and limitations for approval

- Checkout requires authentication and persists COD orders. WhatsApp delivery remains pending a trusted worker/provider; the database queue does not send messages.
- Existing shipping behavior displays EGP 60 up to EGP 1,000 and free shipping above that. The schema intentionally does not encode that display rule; the trusted order service must calculate and persist the correct amount.
- Promotions are not currently applied by checkout. The redemption cap requires a transactional order workflow to enforce under concurrency.
- Channel-aware delivery constraints prevent duplicate queue records, not duplicate external sends in every crash scenario. The worker database contract is present, but a trusted worker runtime/provider and provider idempotency where available are still required.
- The current catalog is sample data and the migration does not seed it. Catalog import/seed values, including product images, should be reviewed separately.
- Order rows and snapshots are retained by design. Define retention/redaction requirements before production if account deletion must erase personal data from historical orders.

### Admin order workflow additions — local and unapplied

The admin order screen already uses `public.transition_cod_order_status(uuid, text, text, text, text)` for confirmation, processing, shipment, delivery, and cancellation; that RPC locks the order, validates transitions, and restores inventory transactionally on eligible cancellations. Payment is a separate field and transition. The current lifecycle RPC does not mark a COD order paid when it is delivered.

The local additive migration `20261106000000_admin_order_history_and_cod_collection.sql` adds two authenticated-session RPCs, both `SECURITY DEFINER` with `set search_path = ''` and an independent `private.is_admin()` check:

- `public.get_admin_order_status_history(p_order_ids uuid[])` reads only status events for 1–100 requested order IDs and returns `order_id`, event ID, from/to status, timestamp, and event shipment fields. It reads the private event table without granting direct table access.
- `public.mark_cod_order_paid(p_order_id uuid)` locks one order and changes `payment_status` from `pending` to `paid` only when `payment_method = 'cod'` and `order_status = 'delivered'`. A repeated call for an already-paid delivered COD order returns success with `newly_paid = false`; incompatible states fail. It does not alter `order_status` or create a lifecycle event. The migration revokes the existing direct `UPDATE(payment_status)` privilege from `authenticated`, so browser clients must use this checked operation.

Execution is revoked from `PUBLIC`, `anon`, `authenticated`, and `service_role`, then granted only to `authenticated`; the function bodies require an authenticated admin. This migration depends on the order and event schemas from `20261021000000_initial_schema.sql` and `20261027000000_order_lifecycle.sql`. It is local implementation only and must be reviewed and applied after earlier pending migrations in filename order before the new status-history panel and COD collection control can work. The existing admin order list continues to load if the history RPC is unavailable and presents a non-sensitive migration notice.

The cancellation choices exposed by the admin UI match the lifecycle SQL: pending confirmation, confirmed, and processing orders may be cancelled; shipped orders may be delivered; the SQL remains authoritative for eligibility and inventory restoration. The UI never equates confirmation/shipment with payment collection.

Admin order-confirmation failures still require the sanitized `admin_order_status_failed` server log entry and its correlation ID to identify the actual failed operation/SQLSTATE. The action's RPC name, named arguments, and array result handling match the local lifecycle migration. No failed request log or authenticated live order state was available during this source review, so the previously reported confirmation failure is not attributed to a specific database or authorization cause. Do not change lifecycle SQL based only on the generic UI message.

The separate administrator email outbox remains defined by the local, unapplied `20261105000000_admin_order_email_outbox.sql`. It fans out from the trusted `order_created` in-app notification, snapshots each admin's email from `auth.users` joined through `public.user_roles`, and uses a distinct private delivery table and service-role-only claim/complete/fail RPCs. The Edge Function processes at most one customer email and one admin email per invocation using the existing Resend adapter. Production delivery still requires applying migrations in order (including `20261104000000_cod_confirmation_conflict_predicate.sql`, then `20261105000000_admin_order_email_outbox.sql`), deploying the function, configuring its server-side Supabase/Resend/scheduler secrets, and configuring a trusted recurring scheduler. No provider request or remote migration was performed for this local implementation.
